# 2.1.2 多 Agent 执行意图与真实启动核对

用户要求并行执行，Plan 正文列出 Agent A/B 分工，批准后原 CLI 仍由主代理单独实施。真实日志没有 invoke_subagent，因此 0 Agents 不是计数丢失。

## 修复

- 从明确用户请求记录多 Agent 执行意图；生成正文里的 Agent 角色名称不会触发执行策略。中文/英文常见执行请求受支持，否定请求不触发。
- Plan 消息显示“尚未启动，批准后才执行”，批准按钮明确“批准并以多 Agent 执行方案”。旧 Plan 可从对应用户请求恢复意图。
- 批准实施及普通模式的明确并行请求注入原生工具指令：同一次 invoke_subagent 调用启动至少两个子代理，划分独立文件范围、提供完整上下文、用 manage_subagents 汇总，不能悄悄降级成单代理。
- 每轮单独去重有效子会话 ID；之前历史中的子代理不能满足新轮次要求。计数继续来自真实 CLI 事件。
- 没有足够子代理就使用主代理实施工具时请求停止，保留触发工具并给出准确错误；结束时不足两个也标记失败。CLI 明确缺少 invoke_subagent 时不发送执行提示。

## 验证和限制

44 项测试通过，覆盖 Plan 不启动、批准后两个 ID、重复事件、0/1 个子代理、旧子代理不能满足新轮次、违规主代理工具、普通方案不会被角色正文误触发、旧记录兼容，以及实际 React → Provider → Coordinator → 模拟 CLI 按钮/卡片链路。

实际 CLI v1.2.14 执行 Plan → 批准 → 两个原生 research 子代理 → 汇总成功。测试工作区没有新增文件；diagnostics/2.1.2-parallel-plan.json 保留实际 ID 与状态。

正常流没有新增模型请求或轮询；仅生命周期变化同步快照。现有 Agent 日志分页/按需订阅不变。

这是执行指令和真实事件核对，不是工具执行前的权限拦截。CLI 工具事件可能在操作已开始后才送达，停止不能回滚已有修改。至少两个真实 ID 证明子代理启动；不同调用下没有可靠重叠生命周期数据时，不声称证明了并行时长。含糊的自然语言、仅“Agent A”不会触发自动并行；需要明确请求“多 Agent 并行执行”。原有子代理权限审批通道限制仍存在。未对用户正在运行的旧轮次改变策略。

确定性性能回放：3 个后台会话、20 张 Agent 卡片、100021 字、1000 工具卡片与 80 MB 工具输出，21 样本文字显示 P95 49 ms，停止 276 ms，输入与向上阅读位置保持通过。见 diagnostics/2.1.2-performance.json；这不是模型等待时间保证。

真实窗口脚本的初次失败记录单独保留：临时文件夹未信任、主代理重复查询 idle 子代理导致超时、脚本未等会话切换/误要求空会话换 ID、复用旧验收工作区时遇到会话锁。验证不操作用户 blender2 的运行任务。
